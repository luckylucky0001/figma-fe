结论
  • 对存量项目，先把「有什么」查清楚，才知道新设计稿能复用什么。figmafe reuse 扫一遍现有 H5（Vue / React / uni-app / Taro + Vant / antd-mobile / NutUI / uni-ui / taro-ui）或 Android（XML View / Compose，QMUI / Material / AppCompat / 自有设计系统）项目，得到组件资产、项目惯例、重复实现和「组件库有但本项目用不了」的组件。figmafe match 再把新设计稿逐个元素对上去，给出「直接复用 / 需确认 / 需新建」，并附上项目里的真实写法和变体 → props 的配置。
  • 准确率：22 个项目 × 3 份设计稿共 726 项，✓696 / △30 / ✗0。其中 17 个是「留出」项目：调规则时没用过，第一次跑出现过错误（见第 2 节），修的都是通用规则，之后作为回归测试。
  • Agent 实测：在 5 个真实项目里按同一份设计稿实现新页面，不用 Skill 的 11 次全部没通过复用检查（Now in Android 里新建了 11～12 个和已有组件重复的组件；Haiku 在 newbee 里一个现成组件都没用），用 Skill 的 11/12 次通过。Haiku 从 0/4 提到 4/4：模型越弱，固定流程的收益越大。
  • 新页面闭环：demo 仓库里，figmafe verify 一条命令输出复用率、违规、像素差异和节点级偏差，退出码可做 CI 门禁；故意埋的 3 处错误全部被抓出，修正后一次通过。
  • 只用免费能力：不用 Figma Code Connect、Dev Mode MCP 和 Variables REST API（都要付费），设计数据走自己写的插件（Plugin API，免费）。

1. 方案：Proposal 的每一条都落成了命令

① 体检存量reuse：资产、惯例、重复概念、复制粘贴结构、写死颜色、版本 / 主题兼容性
② 新稿复用清单match：Figma 元素 → 项目组件，附真实用法、props 配置、可视化叠图
③ 人确认需确认 / 需新建的项写进 component-map.yaml，下次自动采用
④ 实现后检查reuse --focus / --changed：自造轮子、有组件没用、手写已有组件
⑤ 对照设计compare / verify：截图 + 像素 / 节点级偏差，带 Figma 节点 id
⑥ 不许变差--baseline --no-regress 接 CI；偏差沉淀成 rules.md
Proposal 要求落地方式
Figma 组件与代码组件的对应关系match 按名字、UI 概念（中英文同义词）、项目前缀、使用次数、设计系统封装打分；人确认后写进 component-map.yaml，之后 match 优先采用确认过的映射
开发前识别可复用组件先 reuse 再 match：只推荐本项目真能用的组件（检查组件库版本、改名 / 移除、主题依赖、废弃 API、设计系统是否封装过）；没有组件但有固定写法时推荐「项目惯例」
开发后检查用了哪些组件、和 Figma 截图对比reuse --focus <页面> 或 --changed <git ref> 只看新增代码；compare 截图对比；demo 里 verify 把两者合成一个门禁
偏差反馈给 Agent、沉淀规则每条问题都带文件行号或 Figma 节点 id 和修改建议，Skill 规定照着改到通过；决定和理由写进 component-map，经验写进 rules.md

newbee-mall（Vue 3 + Vant）上跑「订单详情」的复用清单：绿框直接复用、橙框需确认、红框需新建；右侧是项目里的真实写法和 Figma 变体对应的 props。

4. 新页面实现闭环（demo 仓库）

  • 自建的 H5（React）和 Android（Compose，兼容 compileSdk 32 / minSdk 23；另有 XML View 存量组件）组件库加一份订单详情设计稿，跑了 13 次 A / C 对照。verify 能区分「页面写错」和「组件本身不符合设计」（Android 剩下的 2 处严重偏差出在组件库内部，见 docs/component-issues.md）；教程第 8 步故意写错 3 处，全部被抓出。
  • 这个仓库小、组件好找，A 组复用率也是 100%，证明不了复用率提升；差别在规范：A 组 7/8 次自造了设计稿外的 CountDown，C 组 0/5。复用率的差距要在真实项目里看（第 3 节）。

5. 局限（如实说明）

  • 没有真实 Figma 文件，本环境也访问不了 Figma：三份设计稿由手写的设计源生成（格式和插件导出一致）。插件只用 mock 的 Plugin API 测过，没在真实 Figma 里跑过。
  • 没有编译真实项目：Agent 实验只做静态检查，没有构建和运行这些开源项目（本环境装不了 Android SDK）；demo 的 Android 截图用 Compose Desktop 渲染，不是真机。
  • 实验有泄漏：A 组 agent 也能看到本仓库的 Skill；1 次 A run 自己跑了 figmafe，已剔除。泄漏只会让 A 组更好，所以 A / C 差距是保守估计。样本量小（每格 1～2 次），只能说明方向。
  • 评分标准是人定的：✓ / △ / ✗ 由我逐条判断并写成回归用例；真实接入时应由组件 owner 复核一次。
