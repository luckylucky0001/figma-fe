Figma → 代码：组件复用与设计还原度

痛点 4 的验证 Demo · 仓库 luckylucky0001/figma-fe · 2026-10-20 · 交付物：CLI figmafe（Go）+ Skill figma-to-code + H5 / Android Demo + 教程
结论
  • 流程跑通、可量化：「先盘点资产 → 建立映射 → 出复用方案 → 实现 → 审计 + 截图对比 → 修正 → 沉淀规则」在 H5（React）和 Android（Compose，兼容 compileSdk 32）两端都实现为一个命令 figmafe verify。它输出复用率、违规、像素差异和节点级偏差，可以直接接入 CI。
  • 实测：10 次对照运行里，C 组（完整 Skill）在 2/2 次 H5 运行中达标。Android 端剩下的 2 处严重偏差都出在组件库内部，A 组和 C 组相同。工具能把「页面写错了」和「组件本身不符合设计」区分开。
  • 如实说明：在这个 demo 里，强模型的基线（A 组）也能找到组件库，复用率达到 100%。差别体现在「规范和可追溯」上：A 组 7/7 次自己造了一个规范外的会跳动的 CountDown 组件，C 组 0/3 次；A 组 1/7 次挂了 Figma 节点 id，C 组 3/3 次。token 漂移、变体缺失这类资产问题，只有 C 组的扫描和映射检查系统性地找了出来。
  • 建议：在真实项目中，先拿一个典型页面按教程接入，用 figmafe verify 量出现状（这是 demo 无法替代的一步），再推广到 PR CI。

verify 能抓到什么（教程第 8 步，故意放了 3 处问题）

读结果

  • 复用率：在组件库就在仓库里、Figma 带组件实例信息的情况下，强模型基线已经能做到 100%。所以在这个 demo 里，复用率不是区分 A、C 两组的指标。真实项目里复用差，通常有这些原因：组件库是独立的包、命名和 Figma 对不上、存在 Legacy 和 Compose 两套组件、仓库太大、设计稿没有组件化。这些需要拿真实项目来量。
  • 规范：A 组每次都自己写了一个带计时逻辑的 CountDown（设计稿里没有这个需求，组件库也没有）。时间一长，这类组件就会变成重复资产。C 组按缺口方案，用静态文本实现，并登记组件需求。
  • 可追溯：C 组每个实例都挂了 Figma 节点 id，偏差可以精确定位到节点。
  • 成本：C 组平均多用约 1.5～2 倍时间，token 多约 20%，换来的是可以复现的验证结果。
  • 闭环有效：第 8 步故意放进的 3 处问题被全部抓到（3 处违规 + 8 处严重偏差），修正后一次通过。

4. 工具校准（实验中发现、已修复）

  • 文本位置改为「左对齐、居中、右对齐任一吻合即算一致」：Figma 文本框常常是定宽，代码里多是按内容收缩，原来按左上角比对会误报（C 组 Agent 发现）。
  • 文本优先匹配纯文本节点，避免匹配到同时带文本的组件根节点（例如 DsTopBar 的标题；C 组 Android Agent 发现）。
  • Android 像素阈值从 4% 调到 5%：实现完全正确时，Skia 和 Chromium 的字形渲染本底约为 4.0%。

5. 局限（诚实说明）

  • 没有真实 Figma 文件，环境也访问不了 Figma：设计数据由独立手写的设计源生成（figmafe fixture），格式和插件导出一致；插件代码没有在真实 Figma 里跑过。
  • 组件库是按规范自建的小型库（两端各 10 个组件），不是你们的真实资产；仓库小，有利于基线 Agent 找到组件。
  • 样本量小（每种条件 1～2 次），结论只能说明方向，不能当作统计显著的结果。
  • Android 渲染用的是 Compose Desktop，不是真机；字体渲染存在本底差异（已经通过阈值吸收）。
